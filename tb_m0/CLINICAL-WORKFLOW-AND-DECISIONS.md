# M0 — clinical workflow, authority, and contract decisions

**Status:** engineering decisions implemented in M0 for a **synthetic hackathon prototype**. This is not a validated clinical pathway, screening protocol, clinical decision support device, or authorization to use real patient data. A qualified Indian TB clinician/local NTEP team must review the pathway and role mapping before any pilot. The four-item symptom intake comes from the supplied project specification; the restrictions below are deliberate M0 safeguards, not claims that the original team document already approved them.

## Decisions to hold constant for M0

| Question | Decision implemented | Why / important boundary |
|---|---|---|
| Age and target population | **Age 18+**, symptomatic adults presenting at an Indian pharmacist/dawa khana or PHC. `patient.demographics.age` must be an integer >=18. | An engineering **demo scope**, not a WHO eligibility cut-off. WHO permits certain adult/adolescent (15+) CXR/CAD screening approaches. Children and locally specialized HIV/pregnancy/extrapulmonary pathways are **out of the prototype's automated logic**, not excluded from real-world care. Escalate to clinician. |
| “WHO four symptoms” | Capture *current cough, fever, night sweats, weight loss*, and optionally cough duration. `true`, `false`, `null` distinguish yes/no/not known. Do **not** label the general-adult intake as validated WHO W4SS or interpret cough >=2 weeks as mandatory. | WHO's specific W4SS *any current cough/fever/night sweats/weight loss* recommendation is for adults/adolescents **living with HIV**. General-population screening algorithms must be chosen based on setting/population. Symptoms guide referral, **not diagnosis**. |
| Roles and permissions | Pharmacist: obtain consent, enter/update symptoms, attach test evidence, submit/resubmit; verifier: review and request additional screening or refer for diagnostics; lab: record specimen/test result; **licensed clinician**: make TB diagnosis/classification and treatment-plan decision; ASHA: navigation/follow-up within assignment. A clinician can additionally act as verifier; a generic verifier is **not** automatically authorized to diagnose. | Server-side authorization must verify actual credentials/assignment in M1/M4. The client-supplied `actor_role` in M0 is an *auditable claim*, **not** access control. |
| Before diagnosis: ASHA | Allowed only for **navigation** (testing appointment, directions, sample transport/check-in) after an authorized verifier request/referral, if locally approved and consented. `support_phase=pre_diagnosis_navigation`; **no medicine pickup log**. | NTEP materials describe health-worker/community support for referral and sample transport; this is **not** treatment initiation or TB diagnosis. Local program must approve delegation. |
| After diagnosis: ASHA | `support_phase=treatment_support` and medicine pickups/follow-up only when a clinician-recorded TB diagnosis **and** `treatment_plan_confirmed=true` exist; `assigned_at` must follow diagnosis. | Bacteriological confirmation, treatment-plan agreement, and **actual treatment initiation** are distinct; recording positive Xpert alone does **not** auto-assign medication tracking. NTEP treats treatment-support assignment as part of treatment initiation. |
| Missing data | `null` is *unknown/not recorded*; `false` is explicitly *no*. Missing X-ray or ESR is acceptable; `available=false` requires its value/result/timestamps all null. A present X-ray image can have no AI inference; no inferred “normal”. Missing symptom answers must never be silently converted to negative. Missing screening markers must not block clinically indicated molecular test referral. | Record a real gap rather than inventing results or requiring extra tests. Missing required identity/consent/core shape causes validation failure and prompts correction, rather than suppressing access to ordinary care. |
| ESR | Optional nonspecific recorded observation; store value and reported reference. Do **not** use an ESR threshold or its absence as TB confirmation, rule-out, or required gate for NAAT referral. | The older `esr_rule.py` threshold is **not approved by M0**; M3 must review its clinical appropriateness. |
| CXR/AI | Optional screening evidence; model flag and raw score never confer diagnosis. `model_confidence` is a **legacy field name**; treat as uncalibrated model score unless validated; `model_id` required if flag present. | Keeps recognizable frozen-schema keys while requiring traceable metadata. Do not call the current prototype model WHO-approved CAD. |
| Bacteriological confirmation | A positive result from an allowed WHO-recognized specimen assay (e.g., Xpert/Truenat, smear, culture) with `test_id`, lab/specimen/time provenance and clinician-recorded classification `bacteriologically_confirmed` citing the positive `test_id`. | Lab *reports* results, clinician *records/accepts* diagnosis and care plan. ESR/CXR/AI/LLM cannot create this classification. |
| Clinical diagnosis | A named licensed clinician records `clinically_diagnosed` when no bacteriologically positive assay is present, with clinical rationale **and decision to give full TB treatment**. If subsequent bacteriology is positive, classification must be updated to bacteriologically confirmed. | This matches WHO and Indian NTEP case definitions. Clinical diagnosis is **not** a shortcut whereby positive symptoms or AI alone auto-confirm TB. |
| Negative/inconclusive diagnostic test | Record accurately, return to clinician for next steps; **do not** automatically close or exclude TB. | Further testing/clinical diagnosis may still be indicated. |
| Consent/data minimization | Store synthetic pseudonymous `patient_ref`, separate visit `case_id`, and captured collection/review-sharing/audio consent. Declined collection/sharing does not create a synced clinical case. No names/phone numbers/raw diagnostic images in fixtures. | Actual consent, revocation, permission enforcement, retention, secure storage and privacy-law review are **not** implemented by M0 schema. |
| Status and syncing | `case_status` = clinical/workflow state in shared record; `revision` = snapshot version; `status_history` preserves state-change provenance. **No `sync_status` in case data**: put `queued/sending/acknowledged/failed`, retries and last ACK in M1's separate **device-local sync envelope**. | A successfully synced case can still be pending tests; keeping statuses separate avoids incorrect workflow transitions and duplicate cases. |

## Clinical decision table (engineering-safe workflow; no automated TB decisions)

| Situation | Authorized actor and action | Next `case_status` | Never infer |
|---|---|---|---|
| Consent recorded; symptom intake complete enough to share | Pharmacist submits case (unknown answers stay null) | `intake → ready_for_review` | No symptom = no TB |
| Symptoms only; X-ray/ESR unavailable | Verifier reviews available information; may refer directly for diagnostic NAAT, request relevant extra screening, or document no referral | `ready_for_review → routed_for_diagnostics` **or** `pending_additional_test` **or** `closed` | X-ray/ESR are mandatory first steps |
| X-ray/ESR already present | Verifier sees source, dates, raw findings and summary; makes explicit human decision | As above | Positive ESR/CAD = confirmed TB |
| Verifier asks for X-ray or other optional extra screening | Create `more_tests_needed` review with `requested_tests`; optional screening route; case retains same `case_id` | `ready_for_review → pending_additional_test` | A mobile unit returns instantly; screen result confirms TB |
| Additional screening arrives | Pharmacist/lab attaches to **same** case; resubmit to qualified reviewer | `pending_additional_test → ready_for_review` | New case ID for each test |
| Verifier elects direct NAAT / confirmatory referral | Record `intervention_required`; create diagnostic route, with appropriate test order | `ready_for_review → routed_for_diagnostics` (also permitted from pending state) | `intervention_required` = diagnosis |
| Specimen collected; result pending | Lab records order/specimen without fabricating result; navigation ASHA may support if approved | `routed_for_diagnostics` | Pending = negative or confirmed |
| Diagnostic laboratory result arrives | Lab records assay, result, specimen, times, site; clinician evaluates | `routed_for_diagnostics → diagnostic_result_available` | Positive result automatically starts treatment-support tasks |
| Bacteriologically positive diagnostic result | Clinician links positive result, confirms classification, makes care-plan decision | `diagnostic_result_available → diagnosed` | AI confirms or selects a regimen |
| Negative/indeterminate result, ongoing suspicion | Clinician decides repeat diagnostics, additional evaluation or clinical diagnosis when warranted | `diagnostic_result_available → routed_for_diagnostics / diagnosed / closed` | A negative test definitively rules out TB |
| No bacteriological confirmation, clinician diagnoses TB | Clinician records rationale and decision to provide a full TB-treatment course | `ready_for_review / routed_for_diagnostics / diagnostic_result_available → diagnosed` | Verifier or pharmacist may diagnose from symptoms alone |
| Actual clinician-documented treatment initiation (after diagnosis and care plan) | Assign ASHA treatment support; only now schedule/pursue medicine pickup logs | `diagnosed` (no forced status transition for assignment) | Screening referral = therapy has commenced |

## Role/action matrix to implement server-side at M1/M4

| Role | Can write | Cannot write |
|---|---|---|
| `pharmacist` | Patient pseudonym/demographics, consent, symptoms, optional results received, submit/re-submit | Referral decision, laboratory-confirmed result as lab, TB diagnosis, treatment plan |
| `verifier` | Human screening review; request additional screening; refer for molecular diagnostics; documented no-referral decision | Formal TB diagnosis or regimen; alter lab assay result |
| `clinician` | All verifier decisions plus diagnostic classification, treatment-plan confirmation and clinician case closure | Forge lab provenance; automate diagnosis without human review |
| `lab` | Diagnostic specimen and assay result; eligible requested-test return | Clinician diagnosis, clinical reviewer decision, treatment support |
| `asha` | Navigation or treatment follow-ups/pickup tracking within assigned phase | Medical diagnosis, treatment prescription, independent diagnostic referral decision |
| `system` | Validated summary suggestions, sync metadata **outside** case, monitoring | Clinical decision or diagnosis; infer missing negatives |

## States and important schema changes from the old frozen document

`intake → ready_for_review → pending_additional_test → ready_for_review → routed_for_diagnostics → diagnostic_result_available → diagnosed → closed` is an **example**, not a forced linear path. Direct referral to diagnostics from `ready_for_review` is valid. `pending_additional_test` can also go straight to diagnostic referral without an optional X-ray/ESR. `diagnosed` can be reached from an eligible review state **only by clinician** in an appropriately documented clinical diagnosis. See `validate_cases.py` for the full explicit allowed-edge/actor table.

- Preserve `case_id`, `patient.demographics`, `symptom_screen`, `xray.model_flag`, `xray.model_confidence`, `esr.value`, and `case_summary` from the original team doc as much as possible. Add `schema_version`, `patient.patient_ref`, `consent`, `revision`, `status_history`, `review_history`, `routes`, `diagnostic_tests`, `diagnosis`, and `asha_assignment.support_phase`.
- **Breaking changes from the old frozen schema**: `status` → `case_status`; `verifier_decision` single object → `review_history` array; `routing` single object → `routes` array; `medicine_pickup_log[].picked_up` boolean → explicit `status`. The intake/sync/X-ray Python modules still need **adapters** in M1/M2/M3; M0 did not pretend they already emit this new format.
- An active diagnostic result is separate from a human diagnosis. A clinician's full-treatment decision, documented actual treatment start (`treatment_started_at`), and a bacteriologically positive laboratory result are separate.
- The M0 checker validates **one snapshot**; a future server must enforce append-only histories, monotonically increasing revisions, verified role credentials, idempotent `case_id+revision` writes and conflict resolution **across snapshots**. This cannot be proven from one JSON file.
